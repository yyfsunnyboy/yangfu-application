## 一、把想法做成東西

我第一次把一個想法變成實體，是國中的多功能智慧遮雨棚。我們整合雨滴、溫溼度與超音波感測器，設計曬衣、看護、花園三種自動模式，App 控制介面由我獨立開發，作品獲得 IEYI 世界青少年發明展臺灣選拔賽銀獎。那時我學會的事情很具體：讓硬體照著我寫的邏輯動起來。

高二選修 Arduino 程式設計時，我做了一套防呆警報器——冷氣開著、房間一段時間偵測不到人，就發出警報。我原本想先在 Tinkercad 上模擬，但紅外線接收器怎麼都讀不到遙控器訊號。後來我改成單獨接上實體 Arduino 與紅外線接收器，先確認程式能正確讀到編碼，再依序加入人體感測器、LED、蜂鳴器與伺服馬達，一個模組一個模組驗證。

那次之後我固定下來一個習慣：把系統拆成輸入、判斷、輸出三段，分開驗證，再逐步整合。比起同時修改程式與電路，這樣才找得到問題真正的位置。這個方法我後來一直在用，只是處理的對象從電路換成了程式結構。

## 二、能寫程式，不等於理解系統

高一下，我為了和朋友爭論球員近期狀態，寫了一支爬蟲去抓 FBref 的資料。單一球員成功之後，我想提高效率，改成一次串接多名球員、連續送出請求。結果程式跑不到一分鐘，我的 IP 就被封鎖了。

我先用 VPN 換 IP，程式順利跑完，但隔天新的 IP 同樣被封。那時我才意識到，這不是一個可以繞過去的技術漏洞。我回頭去查爬蟲的規範，才理解伺服器會針對短時間內的大量請求做 rate limiting，一個有禮貌的爬蟲應該在每次請求之間留下間隔，降低對方負擔。加上請求間隔之後，程式就正常了。

我把抓下來的資料用 pandas 與 xlwings 整合進 Excel，做成球員近期狀態與場上定位的視覺化儀表板，把原本憑感覺的爭論變成可以攤開來看的數據。但這件事真正留下來的，是我當時寫在專題報告裡的一句話：凡事應該先把整個機制搞清楚，再採取行動。

**能寫出可以執行的程式，不代表我理解自己正在使用的系統。**

## 三、從工具走向系統

高二時，我主動去問指導老師趙義雄老師，育秀盃可以做什麼題目。老師要我從真實存在的問題開始找。我想到父親——他在高職教數學，我從小常聽他說，同一個班裡有人跟不上，也有人嫌進度太慢。

我和兩位同學因此開始做 AI 自適應學習系統。在三人團隊裡，我負責的是從教材進入系統、到學生作答回傳的整條資料主線。

**資料庫規劃。** 把課綱依年級、冊次、章節、知識節點分層拆解，並建立節點之間的先後關係。題庫、學習歷程與診斷紀錄都依附在這套結構上，系統才能沿著知識關聯往回追，找出學生真正卡住的位置。

**教材自動化匯入。** 教師上傳 PDF 或 Word 講義後，系統自動解析內容、對應知識節點、建立課綱摘要與例題，並支援批次處理多份教材。這裡我保留了 human-in-the-loop，讓教師可以審核與修改 AI 產生的內容——自動化不應該取代專業判斷。

**Code-as-Content。** 題庫不儲存固定題目，而是儲存「出題程式碼」。一支 Python 腳本可以即時生成大量變題，並由程式精算標準答案，降低生成式 AI 直接產生數學內容時的錯誤。

系統先後獲得神通 AI 數位學院扶輪盃全國第一名，以及育秀盃創意獎高中職 AI 應用類金獎。

但真正影響我後來方向的，是實作過程中發現的一個問題：**由 AI 生成的出題程式，本身也會出錯。** 有時整支程式幾乎都正確，卻只因為一個函式名稱或介面格式的錯誤，就必須重新呼叫模型產生完整程式。那時我開始想：如果錯誤的位置與修法可以確定判斷，是否還需要重新生成整支程式？

## 四、從做出功能，到證明它有效

父親提醒過我，出題系統每次生成程式都要呼叫雲端 API，長期用量會累積成成本。回頭檢視系統的生成紀錄後，我發現同一個數學單元裡，程式結構高度相似，錯誤位置也有重複性。既然錯誤有規律，重複性的工作是不是可以從模型任務中抽離？

我沿著這個想法做了三件事。**Scaffolding Prompt** 把題型規則、可變參數與解題流程結構化後提供給模型，讓它只需要專注邏輯轉譯。**Domain Function** 把重複的數學運算封裝成可重複呼叫的工具。**AST Active Healer** 則是把 AI 生成的 Python 程式轉成抽象語法樹，用四層依序運作的規則修復格式、語法、結構與重複宣告的錯誤——能在不重新呼叫模型的情況下處理掉的局部問題，就不要重新生成。

為了驗證，我設計了一組 3×3 全因子消融實驗：三種模型規模交叉三種系統策略，產出 405 支 AI 生成的 Python 程式，每支生成 5 道題，共 2,025 道數學題，再以我自行建立的 MCRI 指標評分。結果是 41.00 → 94.39 → 97.41，標準差從 34.03 降到 1.67，跨模型、跨運算領域都呈現一致趨勢。

我當時以為自己把問題解決了。

### 兩次被打斷

**東區科展是第一次。** 我們拿到電腦與資訊學科優等，但沒有晉級全國賽。評審指出的問題很明確：作品同時包含出題、推薦、RAG 與程式修復好幾條技術線，功能都能運作，但研究焦點太散，證據不足以回答「究竟是哪一個方法造成改善」。那次我第一次理解到，系統做得出來，不代表研究已經被證明。

**旺宏科學獎的評審問得更深。** 他們沒有問 97.41 有多高，而是問：這個分數是在什麼條件下得到的，又能證明什麼？

回去重新拆解流程之後，我看到三個原本沒有追問的問題。第一，測試題是我從課本例題整理出規則、再要求模型依那套規則生成的——它真的獨立於我的方法之外嗎？第二，MCRI 是我自己設計的評分尺，高分是否就等於生成正確？第三，消融結果顯示 Scaffolding 帶來 +53.39、Healer 帶來 +3.02，但這些提升在獨立資料與更嚴格的驗證下還成立嗎？

評審同時指出，作品中最具實質原創貢獻的是 AST Active Healer，建議把驗證聚焦在這裡做深。

### 重新設計驗證

題目換成公開的國中教育會考試題，不再由我的系統生成。16 題涵蓋四個數學領域，交叉 3 種模型、4 種 Prompt 條件、5 個固定隨機種子，共 960 個實驗單元。其中 4 題 240 格用於規則開發，另外 12 題 720 格作為 held-out 評估——正式評估開始後，不得再依測試結果修改 Prompt 或 Healer 規則。

更重要的是我限縮了 Healer 的權力。決賽版採用 answer-blind 設計：**Healer 看不到正確答案**，只能依固定的 Tier A 到 D 規則判斷，能確定才修，不確定就棄權。因為如果 Healer 可以重新理解題目、重算答案，那麼「修復成功」根本無法證明是修復規則有效。

結果是：720 個 held-out 單元中，342 個原始失敗，Healer 只動了其中 42 個，最後 FAIL → PASS 的有 9 個，安全救援率 2.63%。

這個數字遠比 97.41 難看。但把失敗分成六個層級逐一追蹤之後，它的意義就出來了：救回的 9 格集中在 L2 格式與函式入口（6 格）、L4 執行與資料流（2 格）、L1 語法（1 格）；而 L5 答案或核心演算法錯誤共 144 格，**一格都沒有被修改**。

這不是 Healer 太弱，而是證明 answer-blind 的設計沒有越界去猜答案。Healer 的價值不是把所有錯誤修好，而是只修自己有把握修對的錯誤。

### 那為什麼還需要 Healer？為什麼要用邊緣模型？

重新驗證之後，這個問題變得很尖銳：如果直接呼叫夠強的雲端模型，通過率本來就高，那我做的這些是不是多餘的？

我的答案是，這兩件事處理的不是同一個成本。

雲端大模型很擅長「第一次解決一個沒看過的問題」——理解題意、找出該用什麼運算、組出正確的程式。但 K–12 數學不是開放領域，它受課綱、單元與知識範圍約束，同一個單元的題目會被反覆生成、反覆使用。**真正浪費的不是第一次，是第二次以後的每一次。**

所以我想建立的不是一個更強的生成器，而是一條把成本往下壓的路徑：遇到新題型時，讓較強的模型去理解，並把理解的結果沉澱成 Domain Function 與 Scaffolding，加進可重複使用的工具庫；等到同一類問題再次出現時，邊緣模型加上這些工具與安全的 Healer，就足以在本地重複生成。**不是讓 Edge AI 取代大型模型，而是不要讓大型模型一直重做已經解決過的事。**

Healer 在這條路徑上的位置也因此清楚了。它處理的是那些「規格已經唯一決定、不需要重新思考」的錯誤——介面、資料流、固定格式。這類錯誤如果也要重新呼叫模型，等於為了一個函式名稱付出整支程式的生成成本。至於需要重新理解題意或重算答案的錯誤，Healer 就該棄權，交回模型處理。

延伸驗證支持了這個分工：補齊 Math16 所需的 Domain Function 並提供完整流程說明後，兩個較小的 Qwen 模型原始通過率大幅提升——瓶頸不在修復端，而在前面的模型有沒有拿到足夠的工具，以及知不知道怎麼使用。**工具存在，不等於工具能被正確使用。**

這份研究從 846 件報名作品中進入第二十五屆旺宏科學獎決賽，全領域 20 件決賽作品中，資訊相關僅 4 件。

97.41 沒有消失，統計也沒有變錯。改變的是我對「證明」這件事的理解——分數提升，和方法被充分證明，是兩件不同的事。

## 五、為什麼確定要讀資訊工程

這幾年我做過的東西，表面上跨了硬體、爬蟲、資料分析、學習系統與程式修復，但回頭看，讓我停不下來的一直是同一類問題：**系統為什麼會失敗，失敗能不能被定位，以及我怎麼知道自己真的修好了。**

做出可以運作的產品當然很有成就感。但更吸引我的是產品背後的取捨——什麼該交給模型、什麼該由規則處理、成本要在什麼時間尺度上攤提、一個看起來變好的結果究竟證明了什麼。這些都是資訊工程的問題，而不是應用領域的問題。我的系統長在教室裡，是因為那是我最熟悉、也最容易取得真實回饋的場域；但我想深入的，是生成可靠性、程式分析與系統設計本身。

我也很清楚自己的不足。AST、靜態分析、錯誤修復，我都是為了解決眼前的問題一路自學來的——能用，但沒有理論骨架。2026 年 1 月我參加 APCS 檢測，程式識讀 92 分達第五級，程式實作 135 分為第二級。這個落差很誠實地反映了我的狀態：我讀得懂、也能拆解程式的結構與邏輯，但在演算法實作與效率上還有明顯的成長空間。這正是我需要正式訓練的地方。

另外有一件事我想一起說。這幾年我一直在踢足球，從幼兒園到現在沒有中斷，國三當過隊長，高中連續兩年打進全國五人制前八強。研究大部分時間是一個人做的，球隊不是——輸球是全隊一起輸。這兩件事合起來大概可以說明我是什麼樣的人：可以一個人鑽很久，也待得住一個有輸贏、有隊友、需要長期投入的地方。一份研究被打掉重來，需要的其實是同一種東西。

## 六、申請動機與讀書計畫

### 為什麼是清大資工

我選擇報考大型專案組，是因為我能提出的不是競賽成績，而是一套從真實需求長出來、經過外部檢驗、也被我自己推翻重做過的研究。

會選清大資工，具體的理由有三個。

第一，我需要的基礎訓練正是貴系大一大二的核心：資料結構、離散數學、演算法、計算機組織、作業系統。這些是我目前所有能力的缺口——我靠實作理解了 AST 與靜態分析，但沒有修過編譯器；我做了消融實驗與統計檢定，但沒有系統性學過演算法分析。

第二，貴系大三以上規劃了人工智慧、雲端計算、嵌入式系統等專業領域，這幾條線正好對應我想繼續走的方向：模型可靠性、邊緣運算，以及把生成與修復的成本攤提在雲端與本地之間。

第三，我希望能盡早進入實驗室。這幾年我在學校裡的技術問題，多數只能靠讀原文文件與論文自己解決——GEPT 中高級的聽、閱、說三項單科通過，讓我能直接讀原文資料，但自學終究有上限。我想要的是一個有人能質疑我、也有人能教我的環境。旺宏評審的那幾個問題，比我自己讀一年書學到的還多。

### 讀書計畫

**錄取後到入學前。** 目前這套自適應學習系統正進入父親任教的班級與學校 AI 實驗班，將有四十九位學生實際使用。我會持續維運並累積使用資料，同時補強微積分、線性代數與程式實作，讓高中的專題與大學的訓練不中斷。

**大一至大二：補上理論骨架。** 以資料結構、離散數學、演算法為主，並修習計算機組織與作業系統。我的目標是把「會做」轉成「知道為什麼這樣做」——例如我現在用 AST 走訪程式做修復，但我沒有正式學過語法樹在編譯流程中的位置，也不清楚自己那套四層規則在形式上屬於什麼樣的轉換。

**大二下至大三：往程式語言與可靠性深入。** 修習編譯器設計、程式語言、正規語言等課程，把靠實作摸索出來的 AST 修復接回理論；同時修習人工智慧、機器學習與深度學習，理解模型端的限制。這個階段我希望確認一件事：目前 Healer 的 Tier A–D 規則是我從錯誤樣態歸納出來的，有沒有可能建立在更嚴謹的程式分析基礎上，而不只是經驗規則。

**大三至大四：專題與研究。** 我希望延續目前的題目，往兩個方向擇一深入——其一是生成程式的錯誤型態與安全修復邊界，其二是 Domain Function 與 Scaffolding 的自動累積機制，也就是如何讓系統把「第一次解決問題的成本」自動轉化成「下一次可重複使用的能力」。我也希望爭取國科會大專學生研究計畫的機會。最終題目應該由前期的課程與專題結果決定，而不是現在先替四年後下結論。

**驗證能力的補強。** 系統進入教室之後，我會面對一個新問題：學生的表現變化，究竟是系統造成的，還是其他因素？這是研究設計而非程式的問題，我打算透過相關課程或自學補上這一塊——我在程式層已經學過一次「分數提升不等於方法有效」，我不想在教學層再犯一次同樣的錯。

**更長期。** 我希望能走五年學碩士或學士直攻博士的管道，把這條線做完整。我想做出來的，不是一個只在一個班級、一間學校使用的作品，而是一套能被驗證、能穩定擴充、也能讓不同資源條件的學生都用得到的系統。
