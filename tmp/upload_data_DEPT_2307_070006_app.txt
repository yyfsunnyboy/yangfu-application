B Code-as-Content｜把「出題程式」當成題庫內容
題庫採用我自行設計的 Code-as-Content 做法：題庫先保存題型與教材內容，再由語言模型產
生對應的 Python 出題程式；執行時帶入不同參數，即時產生新的題目與答案。
題型／教材資料→語言模型產生 Python 出題程式→帶入不同參數→即時產生題目＋答案
同一支程式 → 調換題目參數＋對應答案　因此同一題型可以由同一支程式反覆產生不同題目
與答案。

B　研究問題
怎麼讓小模型少做一點，卻做得更可靠？
我觀察到，同一數學單元的程式結構與常見錯誤會反覆出現，於是把問題拆成兩個可以驗證的

Q1｜生成前
哪些重複工作可以事先抽離？
→ Scaffolding／Domain Functions
先整理好題型規則、工具、參數來源與部
分流程，降低模型自己規劃的負擔。
Q2｜生成後
哪些局部錯誤可用固定規則修復？
→ AST Active Healer
只修固定規格能唯一判斷修法的局部錯
誤，把能確定修法的錯誤交給規則處理。
Healer 不是自動修好所有錯誤；無法確定修法時就不介入。

完成。

一整冊教材，難道每一道題都要人工輸入？
後來做成教材匯入系統，整理成冊、章、節、技能與例題資料。
2
如果題目都是固定的，學生怎麼持續練習？
後來把「一題」變成「一支會出題的程式」。
3
AI 可以產生題目，但我怎麼知道它沒有錯？
後來建立生成、檢查、修正、測試到發布的流程。
4
學生做數學需要公式、手寫、作圖與提示，普通表單不夠。
後來做成數學練習介面，並加入 AI 助教。

教材匯入：從 PDF／Word 到結構化教材資料
數學教材同時包含冊、章、節、技能、例題、隨堂練習、習題、自我評量，以及公
式、特殊符號與圖形。如果匯入後這些關係消失，之後就沒辦法可靠地產題、判題，
也找不到學生在哪個技能出錯。若直接將 PDF 交給 AI 處理，這些結構與來源資訊容易
遺失。
因此我設計了一套教材匯入與整理流程：同時讀取 Word 與 PDF，把教材拆成冊、
章、節、技能與每一道題，並保留題目來源。
▲ 匯入系統 V3　選課綱、年級、冊別，
上傳 Word 與 PDF。Word 保留結構與公
式，PDF 保留完整視覺。
▲ 例題管理中心　匯入後拆成章、節、技能與每一道
題，每題保留原始來源（如「1-1 習題 基礎題 1」）與出
題程式狀態。

01｜保留章節結構

03｜保留教材圖片

學校和 Demo 不一樣：少數人試用時，每次都呼叫大型雲端模型看不出問題；數十位
學生長期使用後，API 費用、回應速度與資料外傳都會變成實際問題。所以我讓系統可
以依任務選擇模型，不綁定單一模型。
▲ AI 後台設定（正式系統）　Cloud／Edge／Hybrid 全域切換，依角色配置模型。
能力
教材理解、程式生成與多模態分析需要較強的
雲端模型；簡單提示與固定範圍的互動，小型
本地模型有機會取代部分雲端呼叫。
成本與延遲
雲端模型有 API 成本與網路延遲；本地模型沒
有 API 費用，但取決於主機效能與推論速度。
隱私
可在本機完成的互動留在本機，減少作答與學
習資料不必要的外傳。這只能減少外傳，無法
絕對保證。
三種模式
Cloud 全用雲端；Edge 全用本機；Hybrid 簡
單任務先在本機完成，需要時再交給雲端。
已實作
雲端模型串接（Gemini）、Cloud／Edge／
Hybrid 全域切換、依角色配置模型、本地模型

仍在驗證
不同本地模型的品質與速度、混合調度與
fallback 策略、成本與品質的取捨。目前尚未
證明小型模型足以取代雲端。
